## 写在前面

AI 应用里经常出现一堆概念：`LLM`、`Token`、`Context`、`Prompt`、`Tool`、`MCP`、`Agent`、`Agent Skill`。这些词单独看都不难，但放到一起时，很容易变成一堆散落的名词。

真正理解现代 AI 应用，要把它们串成一条链路：

```text
LLM 是生成引擎
Token 是模型处理文本的基本单位
Context 是模型本次能看到的信息
Prompt 是写进 Context 的任务指令
Tool 让模型影响真实外部世界
MCP 统一工具接入方式
Agent 负责规划和多步调用
Agent Skill 把可复用经验写成结构化规则
```

这篇文章不只解释定义，而是按工程运行逻辑把这些概念打通。

![AI 核心概念链路](/blog-assets/ai-concepts-stack.svg)

## 一、LLM：大语言模型到底是什么

`LLM` 全称是 `Large Language Model`，即大语言模型。它是现代生成式 AI 应用的底层引擎。

从技术脉络看，大语言模型的核心架构来自 Transformer。Transformer 的代表性论文是 Google 团队在 2017 年提出的《Attention Is All You Need》。后续 GPT、Claude、Gemini 等模型都在这个技术方向上不断扩大参数规模、数据规模、训练方式和对齐方式。

但是从使用者角度，可以先把 LLM 理解成一个概率生成器：

```text
输入一段文本
  -> 模型判断下一个 token 最可能是什么
  -> 把生成的新 token 接到上下文后面
  -> 再预测下一个 token
  -> 不断循环，直到生成结束
```

所以，大模型不是“真的在脑子里查答案”，而是在已有输入和训练得到的语言规律基础上，不断预测后续内容。它表现得像在回答问题、写代码、做总结，本质上都是“在当前上下文中生成最合适的后续序列”。

这也解释了几个常见现象：

- 输入越清楚，输出越稳定。
- 上下文越完整，模型越容易保持一致。
- 模型可能编造，因为它生成的是高概率文本，不是天然事实数据库。
- 如果需要实时信息或外部动作，就必须接工具。

## 二、Token：模型处理文本的基本单位

人类读的是字、词、句子，模型处理的是 `token`。

`Token` 可以是一个汉字、一个词的一部分、一个英文词、一段符号，具体怎么切由 tokenizer 决定。模型不能直接理解原始文字，它需要先把文字编码成数字 ID。

完整过程可以拆成两步：

```text
编码：
文本 -> tokenizer 切分 -> token -> token ID

解码：
token ID -> token -> 文本
```

例如：

| 文本 | 可能的 token 切分方式 |
| --- | --- |
| 程序员 | 程序 / 员 |
| 工作坊 | 工作 / 坊 |
| helpful | help / ful |
| 复杂符号 | 可能拆成多个 token |

这里的重点是：`token` 不等于字，也不等于词。不同语言、不同 tokenizer、不同字符类型，切分结果都可能不同。

### Token 为什么重要

Token 会影响三个关键指标：

1. **成本**：很多模型按 token 计费。
2. **速度**：输入和输出 token 越多，计算越慢。
3. **容量**：上下文窗口按 token 限制，而不是按字数限制。

常见粗略换算是：

```text
1 token 大约对应 0.75 个英文单词
1 token 大约对应 1.5 到 2 个汉字
```

这只是估算，不能当成严格换算公式。真正做工程时，最好用对应模型的 tokenizer 统计。

## 三、Context：模型本次能看到的全部信息

`Context` 即上下文，指模型本次处理任务时接收到的全部信息。

它通常包括：

- 当前用户问题
- 历史对话
- system prompt
- developer prompt 或平台规则
- 可用工具列表
- 检索出来的参考资料
- 已生成的中间结果
- 工具返回结果

Context 可以理解成模型的“临时工作记忆”。模型每次输出时，并不是凭空生成，而是基于当前 Context 里的信息继续生成。

这也解释了为什么同一个问题在不同对话里回答可能不同：因为 Context 不同。

## 四、Context Window：上下文窗口容量

`Context Window` 是模型一次能容纳的最大 token 数。它限制了模型本次能看到多少内容。

如果把模型比作一个正在读材料的人，Context 是桌面上摊开的所有资料，Context Window 就是这张桌子的大小。桌子越大，能同时放的材料越多；桌子不够大，就必须取舍。

上下文窗口不够时，会出现几个问题：

- 早期对话被截断。
- 长文档无法一次塞进去。
- 工具返回结果太长，占掉大量窗口。
- 模型看不到关键背景，回答开始偏。

所以工程里不会简单把所有资料都丢给模型，而是会使用 `RAG`。

## 五、RAG：为什么不能把所有材料都塞进 Context

`RAG` 是 `Retrieval-Augmented Generation`，中文通常叫检索增强生成。

它解决的问题很现实：资料很多，但上下文窗口有限，也不想为无关内容付费。

RAG 的基本流程是：

```text
用户问题
  -> 在知识库中检索相关片段
  -> 只把最相关内容放进 Context
  -> 模型基于这些片段生成答案
```

例如有一份上千页产品手册，如果直接全部塞给模型，成本高、速度慢，还可能超过窗口限制。RAG 会先检索“和用户问题最相关的几段”，再交给模型。

RAG 不是让模型变聪明，而是让模型在回答时看见更准确的资料。它的效果取决于：

- 文档切分质量
- 向量检索或关键词检索质量
- 召回片段是否相关
- Prompt 是否要求模型基于资料回答
- 是否有引用、校验和拒答机制

## 六、Prompt：提示词不是玄学，是任务接口

`Prompt` 是写给模型的指令。它可以是用户输入，也可以是系统或开发者提前配置的规则。

低质量 prompt 往往模糊：

```text
写诗
```

这个指令没有说明体裁、主题、风格、长度，模型可能写古诗、现代诗、打油诗，也可能输出完全不符合预期的内容。

更清晰的 prompt 会明确约束：

```text
请写一首五言绝句，主题是秋天落叶，整体风格偏悲凉，不要使用现代词汇。
```

Prompt 的核心不是“写得越长越好”，而是让模型知道：

- 要完成什么任务
- 输入材料是什么
- 输出格式是什么
- 哪些事情不能做
- 遇到不确定情况怎么处理

### User Prompt 和 System Prompt

常见的 prompt 可以分成两类：

| 类型 | 作用 |
| --- | --- |
| User Prompt | 用户当前提出的任务 |
| System Prompt | 系统或开发者给模型设定的角色、边界和规则 |

例如：

```text
User Prompt：
3 加 5 等于几？

System Prompt：
你是一个耐心的数学老师，回答时先引导学生理解过程，再给出答案。
```

模型最终看到的是二者共同构成的上下文。User Prompt 负责表达需求，System Prompt 负责约束行为。

## 七、Tool：工具让模型接触真实世界

LLM 本身只能生成文本。它不知道今天的天气，也不能自己读本地文件、发 HTTP 请求、查数据库、执行代码。

`Tool` 就是把这些外部能力包装成函数，交给模型选择调用。

一个天气工具可以长这样：

```python
def get_weather(city: str, date: str) -> dict:
    return {
        "city": city,
        "date": date,
        "weather": "rain",
        "temperature": "24-29C",
    }
```

用户问：

```text
今天上海天气怎么样？
```

模型并不是自己知道天气，而是判断“这个问题需要调用天气工具”，然后生成工具调用参数：

```json
{
  "tool_name": "get_weather",
  "arguments": {
    "city": "上海",
    "date": "today"
  }
}
```

平台真正执行工具，拿到结果后再把结果交回模型，模型再生成自然语言回答。

![Agent 工具调用与 MCP Skill 流程](/blog-assets/agent-tool-mcp-skill-flow.svg)

### 工具调用里的角色分工

| 角色 | 职责 |
| --- | --- |
| 用户 | 提出原始问题 |
| 模型 | 判断是否需要工具，并生成工具名与参数 |
| 平台 | 解析工具调用，真实执行工具，把结果返回模型 |
| 工具 | 执行外部动作，例如查天气、读文件、调用 API |

这点很关键：**模型不是工具执行者，平台才是执行者。** 模型只是生成结构化调用意图。

## 八、MCP：统一工具接入标准

如果每个平台都有一套工具接入格式，开发者就要为不同平台重复写适配层。一个查询天气工具，可能要给多个模型平台分别写不同的 schema、鉴权、调用协议和返回格式。

`MCP` 即 `Model Context Protocol`，可以理解成模型和工具之间的统一接入协议。

它解决的是工具生态标准化问题：

```text
没有统一协议：
工具 A -> 平台 1 适配
工具 A -> 平台 2 适配
工具 A -> 平台 3 适配

有 MCP：
工具 A -> MCP Server -> 支持 MCP 的客户端或平台
```

可以把 MCP 类比成接口标准。标准化之后，工具不再只服务某一个平台，而是更容易被多个智能体客户端复用。

MCP 的价值主要体现在：

- 降低工具重复开发成本。
- 统一工具发现、调用和返回方式。
- 让本地文件、数据库、浏览器、搜索、代码执行等能力更容易接入智能体。
- 让 Agent 生态更像“可插拔工具系统”。

## 九、Agent：从一次调用到自主规划

普通模型调用通常是一次性的：

```text
用户提问 -> 模型回答
```

Agent 则更像一个能拆任务、选工具、执行多步流程的系统：

```text
用户目标
  -> 分析任务
  -> 制定下一步
  -> 调用工具
  -> 观察工具结果
  -> 决定是否继续
  -> 输出最终结果
```

例如用户说：

```text
查一下我所在地天气，如果下雨，就帮我找附近可以买伞的地方。
```

Agent 可能会这样执行：

1. 调用定位工具，获取当前位置。
2. 调用天气工具，查询当前天气。
3. 判断是否下雨。
4. 如果下雨，调用地图或商家搜索工具。
5. 汇总附近可购买雨伞的地点。

这已经不是单次问答，而是一个带规划、判断和工具调用的闭环。

### Agent 常见实现思想

Agent 不一定只有一种形态，常见思路包括：

- `ReAct`：Reasoning + Acting，边思考边行动，行动后观察结果。
- `Plan-and-Execute`：先制定计划，再按步骤执行。
- `Workflow Agent`：把固定业务流程拆成多个节点，由条件判断驱动。
- `Multi-Agent`：多个角色分工协作，例如规划者、执行者、审核者。

如果任务可预测、流程稳定，Workflow Agent 往往更可靠；如果任务开放度很高，ReAct 或规划式 Agent 更灵活。

## 十、Agent Skill：把经验写成可复用能力

`Agent Skill` 可以理解成给 Agent 使用的结构化技能文档。它不是普通说明书，而是一套可被 Agent 按需读取、按规则执行的操作指南。

一个 Skill 通常会说明：

- 这个技能适合什么场景。
- 触发条件是什么。
- 执行步骤是什么。
- 需要调用哪些工具。
- 判断规则是什么。
- 输出格式是什么。
- 示例输入和示例输出是什么。

不同平台对 Skill 的目录结构和文件名约定可能不同，有的平台使用 `SKILL.md`，有的平台使用 `skill.md`。但核心思想一致：**用结构化文档把隐性经验显性化，让 Agent 在合适场景按固定方法处理任务。**

### Skill 的典型结构

一个 Skill 可以抽象成两层：

| 层级 | 内容 |
| --- | --- |
| Metadata Layer | 名称、描述、触发场景 |
| Instruction Layer | 目标、步骤、规则、工具、输出格式、示例 |

示例结构：

```markdown
---
name: go_out_checklist
description: 根据天气、行程和时间生成出门准备清单
---

# 目标

根据用户要去的地方、出门时间、天气和交通方式，生成可执行的准备清单。

# 执行步骤

1. 读取用户目的地和出门时间。
2. 调用天气工具查询天气。
3. 如果下雨，提醒带伞。
4. 如果光照强，提醒防晒。
5. 如果温差大，提醒带外套。

# 输出格式

先给一句总结，再列出物品清单，每项附带原因。
```

这种 Skill 的作用不是让模型“记住知识”，而是让 Agent 在特定任务里遵循稳定流程。

## 十一、这些概念如何组合成一个 AI 应用

把前面的概念串起来，可以得到一条完整运行链路：

```text
用户提出任务
  -> System Prompt 约束角色和规则
  -> User Prompt 表达具体目标
  -> 输入被 tokenizer 转成 token
  -> prompt、历史、工具列表进入 context
  -> context 受 context window 限制
  -> 模型生成下一步内容
  -> 如果需要外部能力，生成 tool call
  -> 平台执行 tool
  -> tool result 回填 context
  -> Agent 根据结果继续规划
  -> Skill 在特定场景提供稳定操作规则
  -> 输出最终结果
```

这里每一层都有明确职责：

| 概念 | 解决的问题 |
| --- | --- |
| LLM | 负责生成和推理 |
| Token | 负责把文本变成模型可处理的单位 |
| Context | 决定模型本轮能看到什么 |
| Context Window | 限制模型最多能看多少 |
| Prompt | 约束任务目标和输出方式 |
| Tool | 让模型使用外部能力 |
| MCP | 让工具接入更标准化 |
| Agent | 让任务从一次回答升级为多步执行 |
| Agent Skill | 让复杂经验变成可复用流程 |

## 十二、最容易混淆的几个点

### 1. LLM 和 Agent 不是一回事

LLM 是生成引擎，Agent 是围绕 LLM 加上规划、工具调用、状态管理后的系统。Agent 可以调用 LLM，但 Agent 不等于 LLM。

### 2. Context 不是长期记忆

Context 是本次请求里模型能看到的信息。长期记忆通常需要数据库、向量库、文件系统或专门的 memory 机制来维护，再按需写入 Context。

### 3. Tool 不是模型自己执行的

模型只生成工具调用意图。真实调用由平台或运行时执行。

### 4. MCP 不是 Agent

MCP 是工具接入协议，不负责自主规划。Agent 可以通过 MCP 使用工具，但 MCP 本身不是智能体。

### 5. Skill 不是模型训练

Skill 不会改变模型参数，它只是运行时被 Agent 读取的一套结构化规则。

## 十三、工程视角下的学习顺序

如果从零开始理解现代 AI 应用，可以按这个顺序学：

1. 先理解 LLM 如何按 token 生成文本。
2. 再理解 Context 和 Context Window 为什么限制输入容量。
3. 学会写清楚 Prompt，控制任务边界和输出格式。
4. 理解 Tool Calling，让模型能使用外部能力。
5. 理解 MCP，让工具接入更通用。
6. 理解 Agent，把单次工具调用升级成多步任务。
7. 理解 Agent Skill，把反复使用的流程沉淀成可复用技能。

这个顺序比直接学 Agent 更稳。因为 Agent 不是凭空出现的，它是多个基础概念叠加后的工程系统。

## 十四、总结

现代 AI 应用不是只有一个“大模型”。大模型只是核心引擎，真正可用的 AI 系统还需要上下文管理、提示词设计、工具接入、协议标准、任务规划和技能沉淀。

可以用一句话总结整条链路：

```text
LLM 负责生成，Token 承载文本，Context 提供临时记忆，Prompt 定义任务，Tool 连接外部世界，MCP 统一工具接口，Agent 负责任务闭环，Skill 固化可复用经验。
```

理解这条链路后，再看 LangGraph、RAG、Function Calling、MCP Server、代码智能体、浏览器智能体这些工具和框架，就不会只停留在名词层面，而能看懂它们分别解决了系统里的哪一层问题。
