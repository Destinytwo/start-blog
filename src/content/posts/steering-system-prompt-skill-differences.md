## 写在前面

在使用 AI Agent 时，经常会遇到一个问题：为什么同一个模型，在不同平台、不同项目、不同任务里表现差异很大？

有时候它回答得很谨慎，有时候会主动调用工具；有时候会先检查文件，有时候会直接给结论；有时候像一个代码助手，有时候像一个研究助理。这些行为并不完全来自模型本身，而是来自多层约束共同作用。

其中最容易混淆的三个词是：

- `Steering`
- `System Prompt`
- `Skill`

它们都会影响模型行为，但不是同一层东西。简单说：

```text
Steering 是总称：所有引导模型行为的机制。
System Prompt 是全局规则层：规定当前代理的大边界。
Skill 是任务工作流层：规定某类任务具体怎么做。
```

![Steering System Prompt Skill 三层关系](/blog-assets/steering-system-skill-layers.svg)

## 一、先给结论

三者的关系可以这样理解：

| 概念 | 层级 | 作用范围 | 主要解决的问题 |
| --- | --- | --- | --- |
| Steering | 上位概念 | 所有能影响模型行为的机制 | 有哪些东西在引导模型 |
| System Prompt | 全局规则层 | 当前会话或当前代理整体 | 模型整体应该怎么表现 |
| Skill | 任务工作流层 | 某一类具体任务 | 这个任务应该按什么流程执行 |

所以，`Steering` 不是和 `System Prompt`、`Skill` 并列的第三种提示词。它更像一个总集合，`System Prompt` 和 `Skill` 都属于 Steering 的具体形式。

## 二、什么是 Steering

`Steering` 可以翻译成“引导”或“导向控制”。它不是某一段固定文本，而是一类机制的统称。

只要某个东西能改变模型的行为方向、判断标准、执行顺序、工具选择或表达风格，都可以看成 Steering。

常见 Steering 来源包括：

- 系统级规则
- 开发者指令
- 用户当前要求
- 项目级约束
- 工具调用协议
- 输出格式要求
- 检索到的上下文资料
- 任务专用 Skill
- 安全策略和拒答规则

一个 Agent 的最终行为，往往不是由某一条 prompt 单独决定的，而是这些 Steering 来源叠加后的结果。

比如用户要求“帮我改代码”，模型不会只看这句话。它还会受到系统规则、代码编辑规范、仓库当前状态、可用工具、用户历史要求、项目约定、Skill 工作流等多层影响。

## 三、什么是 System Prompt

`System Prompt` 是最接近“总规则”的那一层。它通常在会话开始时就存在，优先级高，持续影响当前代理的行为。

System Prompt 负责规定大边界，例如：

- 模型的基本角色是什么。
- 回答应该使用什么风格。
- 哪些事情允许做，哪些事情不能做。
- 什么时候必须查证信息。
- 什么时候必须使用工具。
- 如何处理高风险问题。
- 是否要遵循特定输出格式。
- 如何处理用户冲突指令。

可以把 System Prompt 理解成代理的“运行环境说明书”。它不负责告诉模型某个具体任务的每一步细节，但会规定这个代理整体上应该怎样工作。

例如一个代码代理的 System Prompt 可能会规定：

- 修改代码前先读上下文。
- 不要回滚用户已有改动。
- 能跑测试就跑测试。
- 不要执行危险命令。
- 最终回复要说明改动和验证结果。

这些规则不会告诉它“怎么写一篇 LangGraph 博客”，但会影响它处理任何任务时的基本方式。

## 四、什么是 Skill

`Skill` 更像某类任务的操作手册。它不是全局规则，而是在特定任务触发时生效。

一个 Skill 通常会说明：

- 适用场景
- 触发条件
- 推荐工具链
- 执行步骤
- 常见坑点
- 需要读取的参考资料
- 输出格式
- 什么叫完成得合格

Skill 的重点不是“定义模型是谁”，而是“告诉模型遇到这类任务时应该怎么落地”。

例如：

| 任务 | Skill 可能规定的内容 |
| --- | --- |
| 读取 PDF | 先提取文本，再渲染页面检查版式 |
| 生成前端页面 | 先识别设计风格，再实现响应式布局，再截图验收 |
| 写技术博客 | 先提炼资料，再重组结构，再补工程解释和配图 |
| 做数据分析 | 先检查字段，再清洗数据，再画图并解释结论 |
| 创建 Agent 项目 | 先定义状态，再拆节点，再确定工具和人工审核点 |

Skill 更像 SOP。它不一定每次都被加载，只有当任务匹配它的适用范围时，Agent 才会读取并执行其中的具体步骤。

## 五、三者为什么容易混淆

它们容易混淆，是因为从外部看，三者都会改变模型输出。

当一个 Agent 回答得更谨慎、更结构化、更像专业工程师时，很容易被笼统地解释成“prompt 写得好”。但实际情况通常是：

- 角色和安全边界由 System Prompt 约束。
- 具体任务流程由 Skill 约束。
- 当前目标由用户 prompt 约束。
- 能不能执行由工具契约约束。
- 能看到什么由 Context 约束。
- 能不能长期保持一致还受记忆和检查点机制影响。

最终看到的输出，是多层约束叠加后的结果。

## 六、用团队协作来类比

可以把 AI Agent 看成一个团队成员。

`System Prompt` 像公司制度和岗位职责：

- 你是谁。
- 你能做什么。
- 你不能做什么。
- 遇到风险怎么处理。
- 输出应该遵循什么基本标准。

`Skill` 像某个具体工作的 SOP：

- 这类任务先做什么。
- 中间检查什么。
- 用哪些工具。
- 结果怎么验收。
- 常见错误怎么避免。

`Steering` 则是所有管理机制的总和：

- 公司制度
- 岗位职责
- 项目规范
- SOP
- 当前任务要求
- 工具权限
- 审核流程

这个类比的关键在于：公司制度不会告诉你按钮放几像素宽，SOP 不会重新定义你是谁。一个管全局边界，一个管局部流程。

## 七、实际工作中它们怎么一起生效

以“让 Agent 写一篇技术博客”为例。

用户请求可能是：

```text
把这份资料整理成博客，优化扩充，写成教程风格。
```

这句话只是当前目标。真正影响结果的还有很多层：

| 层级 | 在这个任务里的作用 |
| --- | --- |
| System Prompt | 要先读资料，不能直接编，最终说明验证结果 |
| 用户请求 | 要写博客，要优化扩充，要教程风格 |
| Skill | 如果有写作 Skill，会规定提纲、资料吸收、配图、校验方式 |
| 工具契约 | 只能通过文件读写工具修改仓库，不能随便破坏文件 |
| 项目结构 | 博客必须放进 `src/content/posts`，frontmatter 要符合 schema |
| 构建系统 | 文章必须通过 Astro 内容检查和构建 |

所以最后生成的博客不是单靠“写一篇博客”这句话完成的，而是多个约束共同塑形。

## 八、从优先级看三层约束

不同平台对优先级的实现细节不完全一样，但工程上可以按下面这个方向理解：

```text
平台和安全规则
  -> System Prompt / Developer 指令
  -> 项目级规则
  -> Skill 工作流
  -> 用户当前请求
  -> 模型默认倾向
```

这不是严格协议顺序，但能帮助判断一个问题：如果 Agent 行为不符合预期，应该改哪一层？

| 问题 | 更可能应该改哪一层 |
| --- | --- |
| 模型总是违反安全边界 | System Prompt / 安全规则 |
| 模型每次做某类任务顺序都不对 | Skill |
| 某次任务目标没表达清楚 | 用户 Prompt |
| 工具参数总是错 | 工具 schema 或 Skill 示例 |
| 输出格式不稳定 | System Prompt 或 Skill 输出规范 |
| 项目内流程不一致 | 项目规则或 Skill |

如果把所有问题都归因于 prompt，就很难定位问题。先判断是哪一层约束失效，修改才有效。

## 九、System Prompt 适合写什么

System Prompt 适合放全局、稳定、跨任务都成立的规则。

适合写入 System Prompt 的内容：

- 代理身份和职责
- 安全边界
- 高风险任务处理方式
- 工具使用基本原则
- 信息核验要求
- 输出风格要求
- 与用户协作方式
- 冲突指令处理规则

不适合写入 System Prompt 的内容：

- 某个项目的一次性细节
- 某类任务的超长执行清单
- 大量示例代码
- 只在极少场景使用的专用流程
- 可以按需加载的参考资料

System Prompt 过长会挤占上下文，也会让模型在每个任务里背着大量无关规则。全局规则应该稳定、简洁、边界清楚。

## 十、Skill 适合写什么

Skill 适合放具体、可复用、任务相关的流程。

适合写入 Skill 的内容：

- 某类任务的标准步骤
- 推荐工具和命令
- 输入输出格式
- 常见错误
- 验收标准
- 示例输入和输出
- 需要读取的参考文件
- 可复用脚本说明

不适合写入 Skill 的内容：

- 所有任务都必须遵守的安全规则
- 代理身份定义
- 与当前技能无关的大量知识
- 临时的一次性需求

Skill 的价值在于按需加载。平时不占用上下文，只有任务匹配时才展开详细规则。

## 十一、Skill 和普通提示词的区别

普通提示词通常是一次性的，用户说完这次任务就结束了。

Skill 则是可复用的、结构化的、带触发条件的任务规范。

| 维度 | 普通 Prompt | Skill |
| --- | --- | --- |
| 生命周期 | 当前请求 | 可长期复用 |
| 结构 | 可自由表达 | 通常有元数据、步骤、规则 |
| 触发方式 | 用户直接输入 | 根据任务匹配按需加载 |
| 作用 | 表达当前目标 | 固化某类任务的执行方法 |
| 适合内容 | 一次性要求 | 反复出现的工作流 |

所以 Skill 不是“更长的 prompt”，而是把某类任务沉淀成可复用能力。

## 十二、Tool 契约也是一种 Steering

很多人只关注文本提示词，但工具本身也会引导模型行为。

一个工具的名称、描述、参数 schema、返回格式，都会影响模型是否调用它，以及怎么调用它。

例如两个工具：

```text
search_web(query: string)
get_current_weather(city: string, date: string)
```

当用户问“明天武汉会下雨吗”，模型更容易选择 `get_current_weather`，因为工具名和参数契约明确表达了适用场景。

如果工具描述含糊，参数设计混乱，模型就容易：

- 选错工具
- 漏掉必填参数
- 生成错误参数
- 把不该交给工具的任务交给工具
- 拿到工具结果后总结不稳定

因此，工具 schema 不是纯工程细节，它也是 Steering 的一部分。

## 十三、在 Agent 项目里怎么设计这三层

构建复杂 Agent 项目时，可以按三层来拆规则。

### 1. 全局层：System Prompt

放稳定边界：

- 代理身份
- 风险控制
- 工具调用原则
- 信息核验要求
- 输出基本规范

### 2. 任务层：Skill

放任务流程：

- 数据分析怎么做
- 报告生成怎么做
- 代码修改怎么做
- 文档整理怎么做
- 异常复核怎么做

### 3. 执行层：User Prompt 和 Runtime Context

放当前任务变量：

- 本次目标
- 输入文件
- 时间范围
- 输出要求
- 用户偏好
- 当前工具结果

这样拆分后，系统更容易维护。全局规则变化时改 System Prompt；某类任务流程变化时改 Skill；本次目标变化时改用户请求或运行时参数。

## 十四、常见反模式

### 1. 把所有东西塞进 System Prompt

这样会导致上下文臃肿，也会让模型在无关任务里背负过多规则。System Prompt 只适合放全局稳定规则。

### 2. 每次都重新写长 Prompt

如果一类任务反复出现，每次都手写长提示词，说明它应该沉淀成 Skill。

### 3. Skill 只写愿望，不写步骤

例如只写“请高质量完成设计任务”，价值很低。Skill 应该写清楚执行顺序、工具选择、检查点和验收标准。

### 4. 工具描述过于抽象

工具描述如果只写“用于查询信息”，模型很难判断何时调用。工具名、参数和描述要尽量具体。

### 5. 用户请求和系统规则互相冲突

如果用户临时要求覆盖系统边界，Agent 应该遵守更高层规则，而不是盲目执行当前请求。

## 十五、调试 Agent 行为时怎么定位

当 Agent 行为不符合预期，可以按这个顺序排查：

1. 是否是用户任务描述不清楚。
2. 是否是 Skill 没有被触发。
3. Skill 是否缺少关键步骤或示例。
4. 工具 schema 是否表达不清。
5. System Prompt 是否给了相反约束。
6. Context 是否缺少关键资料。
7. 模型是否需要更明确的输出格式。

不要一上来就重写全部 prompt。先判断是哪一层出了问题。

## 十六、总结

`Steering`、`System Prompt` 和 `Skill` 的区别，可以压缩成一句话：

```text
Steering 是总称，System Prompt 管全局边界，Skill 管具体任务流程。
```

理解这三层后，很多 Agent 行为会变得更容易解释：

- 它为什么用这种语气回答？
- 它为什么必须先查证？
- 它为什么先读文件再改代码？
- 它为什么在某类任务里固定按某个流程走？
- 它为什么有时调用工具，有时不调用？

答案往往不是“模型自己想这样”，而是多层约束共同作用的结果。

对于真正要落地的 AI Agent 项目，最重要的不是把 prompt 写得越来越长，而是把规则放到正确的层级：全局边界放 System Prompt，任务方法沉淀成 Skill，工具能力用清晰契约暴露，当前需求交给 User Prompt。这样 Agent 才更可控、更稳定，也更容易迭代。
